# Assumptions & Design Decisions

This document outlines the architectural decisions, business rules, and domain assumptions made during the design and implementation of the **Transaction Ledger API**.

---

## 1. Account Lifecycle & Balances
- **Initial Balance Rule**: In strict compliance with ledger banking standards, the client cannot set the initial balance. The initial balance is always initialized to `0.00`. If a request payload attempts to send `balance` or `initial_balance`, it is rejected with `400 Bad Request` (`VALIDATION_ERROR`).
- **Account Identifier (`id`)**: The system generates a standard UUID v4 string upon account creation. This guarantees uniqueness, eliminates sequential enumeration attacks, and avoids relying on database-internal identifiers (`_id`).
- **System Timestamps**: The `created_at` timestamp is generated by the server using `Date.now()` upon insertion and is marked immutable.

---

## 2. Transactions & Ledger Integrity
- **Monetary Precision**: All amounts represent currency and are validated to be strictly positive numbers (`> 0`) with at most 2 decimal places (representing cents/paisa). Values are rounded to 2 decimal places to avoid standard IEEE 754 floating-point drift.
- **Allowed Types**: Only `'credit'` and `'debit'` transaction types are allowed.
- **Overdraft Policy**: Debit transactions require `account.balance >= amount`. Accounts cannot have negative balances; attempts to debit more than the current balance are rejected with `422 Unprocessable Entity` (`INSUFFICIENT_BALANCE`), leaving the balance unchanged.
- **Reference ID Idempotency**:
  - `reference_id` must be unique **per account**.
  - A compound unique database index `{ account_id: 1, reference_id: 1 }` guarantees this at the database level.
  - If a duplicate `reference_id` is supplied for the same account, the request is rejected with `409 Conflict` (`DUPLICATE_TRANSACTION`), creating no transaction and leaving the balance untouched.
  - The same `reference_id` **may** be used for different accounts (e.g. shared invoice numbers or external bank transaction IDs across multiple counter-parties).
- **Immutability**: Once written, transaction records cannot be modified or deleted. No `PUT`, `PATCH`, or `DELETE` endpoints are exposed. Any request directed to `/accounts/:id/transactions/:txId` receives an explicit rejection with code `TRANSACTION_IMMUTABLE`.

---

## 3. Atomicity & Concurrency Model
- **Replica Set & Atlas Support**: When connected to a MongoDB cluster with replica sets enabled, all balance changes and transaction creations are executed inside ACID multi-document transactions using `session.withTransaction()`.
- **Standalone MongoDB Fallback**: To ensure seamless local execution without requiring a configured replica set, the service supports atomic conditional queries (`findOneAndUpdate({ balance: { $gte: amount } })`) coupled with compensating rollback hooks, ensuring 100% balance consistency in all environments.

---

## 4. History, Filtering, Pagination & Sorting
- **Sorting**: All transaction history queries return records strictly in latest-first order (`created_at: -1`).
- **Filtering**: Supports filtering by `type=credit` or `type=debit`. Omitting the `type` parameter returns both types.
- **Pagination**: Supports `page` (default: 1) and `limit` (default: 10, max: 100). Metadata returned includes `current_page`, `page_size`, `total_records`, and `total_pages`.

---

## 5. Bonus: Money Transfer
- **Double-Entry Ledger Consistency**: A transfer generates two atomic ledger transaction records:
  1. A `debit` entry on the source account (`reference_id`: `transfer_<ref>_debit`).
  2. A `credit` entry on the destination account (`reference_id`: `transfer_<ref>_credit`).
- **Master Transfer Record**: An immutable record in the `transfers` collection with unique `reference_id` links the two transaction IDs.
- **Atomicity**: If either account fails (insufficient funds, missing destination account, network failure), the entire operation rolls back. Partial transfers are impossible.
- **Self-Transfer**: A transfer where `source_account_id === destination_account_id` is rejected with `400 Bad Request`.
